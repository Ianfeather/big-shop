7. ~~Generate an OpenAPI spec for the Go API.~~ **Resolved** — migrated `internal/pkg/app` from raw `net/http`/`gorilla/mux` handlers to [Huma](https://github.com/danielgtaylor/huma) (`humamux` adapter on the same `mux.Router`, so routing/middleware are unchanged). Each operation's typed Input/Output struct is both the request/response binding *and* the OpenAPI schema source, so the two can't independently drift the way a hand-annotated spec could. Spec is committed at `docs/openapi.yaml`, regenerated via `go run . openapi` (no DB required), with `build.sh` failing the build on drift. Pinned to `huma/v2@v2.35.0` — the latest version supporting go 1.23 (matches `netlify.toml`'s `GO_VERSION`); newer releases require go 1.24+. One route was reshaped: `GET /recipe/{slug:[a-zA-Z-]+}` and `GET /recipe/{id:[0-9]+}` (two mux routes disambiguated by regex) became a single `GET /recipe/{id}` (tries `strconv.Atoi` first, falls back to slug lookup) since gorilla/mux's per-segment regex constraints leak verbatim into Huma's generated path templates. Adopting Huma's schema-derived request validation also surfaced three real, pre-existing gaps between the frontend's actual request payloads and the Go structs used to bind them — fixed as part of this migration since they'd otherwise have newly 422'd in production: `common.Recipe.ID` (POST /recipe sends no `id` for a new Recipe), `common.User.ID`/`Name` (POST /user and /invite send partial bodies), and `common.Ingredient.Department` (the frontend never supplies it — it's resolved server-side from `ingredient_department`). All now `omitempty`. `DELETE /recipe` got its own minimal `{id}` input type rather than widening `common.Recipe` further, since doing that would have made `omitempty` start silently dropping empty `ingredients`/`tags` arrays from `GET /recipe/{id}` responses (breaking `.map()` calls on the frontend for recipes with no ingredients/tags).

10. ~~`ShoppingList`'s department sort comparator looks inverted/buggy.~~ **Resolved** — `components/shopping-list/ShoppingList/index.js`'s `sortByDepartment` is now a priority-based comparator (`DEPARTMENT_ORDER = ['meat and fish', 'other', 'vegetables']`, unknown/missing departments sort last of all) instead of the old ad-hoc branching, which returned the wrong sign for the vegetables case and `undefined` (silently treated as `0`) for several department pairings. 12. ~~Add e2e tests using playwright that cover the most common user flows, running locally.~~ **Resolved** — Playwright added, scoped to `e2e/` (TypeScript, its own `tsconfig.json`; rest of the repo stays plain `.js` per the still-open #9). `npm run test:e2e` runs `e2e/recipe.spec.ts` (add/edit/delete a Recipe - each test creates its own uniquely-named fixture and cleans up via a direct API call in `afterEach`, never through the UI's "Parse ingredients" box since that hits a real LLM) and `e2e/shopping-list.spec.ts` (add/remove a Recipe on the list, add an Extra Item, mark/un-mark an item bought, clear the list - run `test.describe.configure({ mode: 'serial' })` in a fixed order since the Shopping List is one singleton resource per Account under `DISABLE_AUTH`, bracketed by a `DELETE /shopping-list/clear` in `beforeAll`/`afterAll` so the suite is correct regardless of what a previous run left behind). `npm run test:e2e:debug` runs the same suite headed and slowed down (`E2E_SLOWMO`) for stepping through a scenario visually. 14. **Open: deselecting your only selected Recipe on the Shopping List doesn't clear its Ingredient Items.** `pages/list.js`'s `getShoppingList()` has `if (!selectedRecipes.length) { return; }` - when unchecking a Recipe brings the selection down to zero, this skips the `POST /shopping-list` call entirely, so the last-selected Recipe's Ingredient Items stay displayed (stale) until a *different* Recipe gets selected (which does trigger a real, non-empty regenerate) or the list is cleared. Only affects the single-recipe case; found while writing `e2e/shopping-list.spec.ts`'s "remove a recipe" test (worked around there by keeping a second Recipe selected throughout, which is also the more realistic scenario).

16. ~~`pages/api/recipe-image.mjs` imported a `Blobs` class from `@netlify/blobs` that doesn't exist.~~ **Resolved** — found while converting the file to TypeScript (item 9): the installed version (`8.1.2`) only exports `Store`/`getStore`/`getDeployStore`, no `Blobs` class at all. `new Blobs(...)` would have thrown `TypeError: Blobs is not a constructor` on every invocation, meaning Photo Import's job-status persistence (the `updateJobStatus` helper, used by both the job-creation POST and the job-status-poll GET) was completely non-functional in production. Switched to `getStore({ token, siteID })`. The `{ ttl: 3600 }` option passed to `.set()` also isn't part of this version's `SetOptions` — dropped, since it was already inert given the above.

17. **Open: `pages/api/dave/tools.ts` and `chat.ts` type recipe/OpenAI data as `any`, hiding a dead field.** Found during a targeted post-migration review of `any`/`!`/`as` usage introduced by item 9's TypeScript sweep. `tools.ts`'s `allRecipes: any[]`/`(recipe: any) =>` reads `recipe.description` in three places (search filtering, mapped results, display text), but `Recipe`/`RecipeSummary` in `types/api.d.ts` have no `description` field at all (`id, ingredients, method, name, notes, remoteUrl, tags`) — so it's always `undefined`, silently disabling description-based search/display. Pre-existing bug carried over from the old `.js`, not introduced by the migration, but typed properly it would have failed to compile instead of failing silently. `chat.ts`'s `openAIMessages: any[]`/`toolMessages: any[]` have the same issue in kind, if not yet in observed impact: real `ChatCompletionMessage`/tool-result shapes are pushed on with no compile-time check, so a future edit dropping a required field (e.g. `tool_call_id` on a `role: 'tool'` message) won't be caught until OpenAI's API rejects the request at runtime.

18. **Open: `NETLIFY_BLOB_STORE_TOKEN`/`SITE_ID` and Auth0 `domain`/`clientId` are asserted non-null (`!`) rather than validated at startup.** Same review as item 17. `pages/api/recipe-image.ts`'s two `getStore({...})` call sites do `process.env.NETLIFY_BLOB_STORE_TOKEN!`/`NETLIFY_SITE_ID!` — if unset (e.g. a preview deploy without Netlify Blobs configured), this throws unhelpfully deep inside `getStore()` instead of failing clearly. `pages/_app.tsx`'s `domain={domain!}`/`clientId={clientId!}` for `Auth0Provider` have the same shape: gated only by the `authDisabled` flag, not an actual check that the env vars are non-empty, so a misconfigured deploy with auth enabled passes `undefined` straight through the assertion. Fix would be an explicit startup check (fail fast with a clear error) rather than deferring to a runtime assertion at point of use.

19. **Open: `pages/recipes/[id]/edit.tsx` and `index.tsx` cast `router.query as { id: string }` without guarding `router.isReady`.** Same review as item 17. Before `router.isReady`, `router.query` is `{}`, so the cast asserts something false on first render and `useRecipe(id)` fires `GET /recipe/undefined`. Not a new regression — same behaviour existed in the old `.js` — but the cast formalises the lie rather than guarding it, and it's the same class of timing issue CLAUDE.md's "known rough edge" section already documents for this route. The identical cast + comment is duplicated verbatim across both files — worth extracting to a small `useRecipeIdParam()` hook alongside the fix.
