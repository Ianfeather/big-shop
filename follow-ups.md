7. ~~Generate an OpenAPI spec for the Go API.~~ **Resolved** — migrated `internal/pkg/app` from raw `net/http`/`gorilla/mux` handlers to [Huma](https://github.com/danielgtaylor/huma) (`humamux` adapter on the same `mux.Router`, so routing/middleware are unchanged). Each operation's typed Input/Output struct is both the request/response binding *and* the OpenAPI schema source, so the two can't independently drift the way a hand-annotated spec could. Spec is committed at `docs/openapi.yaml`, regenerated via `go run . openapi` (no DB required), with `build.sh` failing the build on drift. Pinned to `huma/v2@v2.35.0` — the latest version supporting go 1.23 (matches `netlify.toml`'s `GO_VERSION`); newer releases require go 1.24+. One route was reshaped: `GET /recipe/{slug:[a-zA-Z-]+}` and `GET /recipe/{id:[0-9]+}` (two mux routes disambiguated by regex) became a single `GET /recipe/{id}` (tries `strconv.Atoi` first, falls back to slug lookup) since gorilla/mux's per-segment regex constraints leak verbatim into Huma's generated path templates. Adopting Huma's schema-derived request validation also surfaced three real, pre-existing gaps between the frontend's actual request payloads and the Go structs used to bind them — fixed as part of this migration since they'd otherwise have newly 422'd in production: `common.Recipe.ID` (POST /recipe sends no `id` for a new Recipe), `common.User.ID`/`Name` (POST /user and /invite send partial bodies), and `common.Ingredient.Department` (the frontend never supplies it — it's resolved server-side from `ingredient_department`). All now `omitempty`. `DELETE /recipe` got its own minimal `{id}` input type rather than widening `common.Recipe` further, since doing that would have made `omitempty` start silently dropping empty `ingredients`/`tags` arrays from `GET /recipe/{id}` responses (breaking `.map()` calls on the frontend for recipes with no ingredients/tags).

20. **Open: replace `use-http` with a Strict-Mode-safe data-fetching library (SWR or TanStack Query) for read/GET requests.** Found debugging a crash in `components/recipe-form/Form.tsx` (fixed directly — see CLAUDE.md's "Known rough edge" section for the full mechanism): `use-http` registers `request.abort` as a mount effect's cleanup, so React Strict Mode's double-invoke aborts a component's first-pass request(s) before the real second pass completes. Where a component fires several concurrent requests off one shared `useFetch` instance, this is worse than "occasionally renders empty" — the hook's single `response`/`error` reflects whichever call last resolved, not each one individually, so gating multiple `setState`s behind one shared `response.ok` can silently apply state from a *different* call than the one that just got aborted. Form.tsx's fix was local (check each result for `undefined` individually instead of trusting `response.ok`), but that's a pattern every future multi-concurrent-call site has to remember to apply by hand — worth a quick grep for other `Promise.all([get(...), get(...)])`-on-one-instance call sites to gauge current exposure. SWR/TanStack Query dedupe and cache by key, so Strict Mode's second pass reuses the first's in-flight request instead of racing a separate one, and neither has a shared-mutable-response-across-concurrent-calls concept to race on at all. Sizable migration though — `use-http` is used across most of the app's data-fetching call sites (including POST/PUT/DELETE, which these libraries don't cover the same way) — so this is a deliberate future data-layer decision, not something to trigger off one bug alone.
