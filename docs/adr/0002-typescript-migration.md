# TypeScript migration: full sweep, strict, OpenAPI-generated API types

The frontend (`pages/`, `components/`, `hooks/`, and `pages/api/*`, including their tests) is converting from plain `.js` to TypeScript in one bounded sweep, not an incremental `allowJs`/`checkJs` adoption. `strict` mode and a blocking `tsc --noEmit` check land in `build.sh` from the first PR, not as a later tightening pass. The work is sequenced as four PRs in dependency order — (1) `tsconfig.json` + build/CI wiring + codegen, (2) `hooks/`, (3) `components/`, (4) `pages/` + `pages/api/` — so each is independently reviewable without ever landing a mixed, partially-typed codebase as the end state. Each PR's merge gate is `tsc --noEmit` passing for its scope plus `npm run test` passing — test files convert alongside the code they cover, so the existing Vitest suite keeps exercising runtime behavior throughout the sweep rather than just the compiler's static checks.

Incremental adoption (loose `allowJs`/`checkJs`, converting files opportunistically as they're touched) was considered and rejected: it's the standard advice for large codebases where a full sweep is too disruptive, but this frontend is small enough that the layered PR sequence gets the same review-size mitigation without the multi-year tail of mixed `.js`/`.ts` that incremental adoption usually produces.

Types for what the Go API returns (`Recipe`, `Account`, `ShoppingList`, etc.) are generated by `openapi-typescript` from `docs/openapi.yaml` into `types/api.d.ts`, rather than hand-written. `build.sh` already fails the build if `docs/openapi.yaml` drifts from the Huma-derived spec in `app.go`; chaining a second generate-and-diff step keeps frontend types honestly derived from that same source instead of a hand-maintained set that could silently drift from what the Go handlers actually return. `types/api.d.ts` is committed (not gitignored), so it participates in PR review the same way `docs/openapi.yaml` already does.

**Consequence worth knowing:** `mocks/*.json` (served when `NEXT_PUBLIC_USE_MOCKS=true`) is left as plain JSON rather than rewritten as `.ts` and asserted against the generated types — `resolveJsonModule` lets TypeScript infer each file's shape structurally instead. A mock missing a field a real caller needs is still caught wherever that field is used, just not at the mock file itself. Separately, `swagger-ui-react` (used in `pages/_app.js` and `pages/dev/api-docs.js`) ships no type definitions and has no `@types` package; it gets a local ambient shim at `types/swagger-ui-react.d.ts` rather than blocking the sweep on it — this is a deliberate, narrow exception, not something to "fix" by chasing down real types later.
